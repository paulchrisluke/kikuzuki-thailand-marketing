# Proposal: retire database epochs

Status: proposal. Supersedes nothing yet. Written after the Epoch 6 production
cutover on 2026-09-08.

## The claim

The epoch is not a migration strategy. It is a database rebuild we perform
instead of writing a migration, and it is the direct cause of every production
freeze we have taken.

## What Epoch 6 actually changed

Measured by diffing the archived Epoch 5 baseline against the shipped Epoch 6
baseline:

| | Epoch 5 | Epoch 6 |
| --- | --- | --- |
| Tables | 53 | 52 |
| Tables removed | — | `usage_quota_grants` |
| Tables added | — | none |
| Columns removed | — | `customers.last_booking_at`, `customers.last_review_at` |
| CHECK constraints | 190 | 223 |

That is the whole schema delta: drop one table, drop two columns, tighten
constraints. The rest of the epoch was data reconciliation — `editor_mode`
backfill, machine-key alt text set to `NULL`, block residue removal, social-post
visibility projection — which is `UPDATE` work, not schema work.

## What it cost

To drop one table and two columns:

- A new production D1 resource, provisioned and bound.
- A 298-line single-use transfer tool, `scripts/epoch6-data.mjs`, which the
  cutover document notes "replaces the retired Epoch 5 transfer tool".
- A production write freeze: **14 minutes of HTTP 503 on all four sites**,
  22:01:28Z to 22:15:19Z.
- A frozen export, offline transform, offline verify, remote baseline apply,
  24 MB data-only import, remote re-export, and a full hash comparison of
  44,255 rows.
- Seven staging candidate databases across the epoch's qualification.
- 274 lines of cutover documentation, on top of 1,062 lines across the five
  previous epoch documents.

The transfer itself was flawless: 52 tables, 44,255 rows, per-table logical
hashes identical, foreign keys clean, integrity ok, on the first attempt. That
is the point. The expensive, carefully verified part is not the part that fails.

## The rule that manufactures all of it

`docs/operations/release-and-outage-prevention.md:124`:

> Never rewrite migration history for a production or rollback D1 database
> resource. Rebaselining production schema history requires a database epoch:
> provision a new production resource, apply one generated baseline, transfer
> and verify data explicitly, cut bindings over under the documented write
> freeze, and retain the old production resource for rollback.

Everything follows from the first sentence. The ledger may not be rewritten, so
a clean baseline needs a new database; a new database needs the rows moved; moving
rows needs them to hold still; holding them still is the outage. The schema change
never required any of it.

## Why the justification does not hold for Epoch 6

Epochs 2 through 5 squashed genuine accumulated history — 205 incremental
migrations exist in the repository's history, up to `0136_gorgeous_black_queen.sql`.
Squashing that was defensible.

Epoch 6 squashed nothing. `migrations-archive/epoch-5/` contains exactly one file,
`0000_epoch_5_baseline.sql`. Between Epoch 5 shipping and Epoch 6 starting, **zero
incremental migrations were written.** There was no history to rebaseline. The
epoch machinery ran to produce a baseline that was already one file.

## What the same change looks like as ordinary migrations

```sql
-- 0001_retire_usage_quota_grants.sql
DROP TABLE usage_quota_grants;
ALTER TABLE customers DROP COLUMN last_booking_at;
ALTER TABLE customers DROP COLUMN last_review_at;
```

```sql
-- 0002_publication_state.sql   (SQLite cannot ALTER a CHECK; rebuild the one table)
-- standard 12-step table rebuild, generated by drizzle-kit, scoped to content_documents
```

```sql
-- 0003_reconcile_block_data.sql  (the editor_mode / alt text / residue backfill)
```

No new resource. No transfer tool. No export, import, or hash comparison. No
freeze, because `DROP COLUMN` and a single-table rebuild do not require the
database to hold still. Roughly three files against a 298-line program plus a
274-line procedure.

The genuinely awkward part is real and worth naming: SQLite cannot alter a CHECK
constraint in place, so constraint changes need a table rebuild. That is a
*per-table* rebuild inside a normal migration — a documented, generated, routine
operation — not a whole-database epoch.

## What this predicts about the failures

Every failure on the night of 2026-09-08 lived in the machinery, not the schema:

| Failure | Exists without epochs? |
| --- | --- |
| Search index refresh raced the freeze and got our own 503 | No — there is no freeze |
| Production verification asserted seeded demo fixtures | Yes — independent test defect |
| NCLS home 404 on a rotating `_nuxt` chunk mid-rollout | Reduced — one deploy, not two |

Two of the three are artifacts of the cutover. They cannot be caught earlier by
moving gates around, because they only exist during a procedure that ordinary
migrations do not have.

## The staging question

Staging runs 2,816 generated fixture rows; production runs 44,255 rows of
imported customer content. Staging therefore answers "does this code work on data
we invented?" — never "does this code work on data we inherited?"

Concretely, staging cannot see production's imported shapes: `h4` nested directly
under `h2` with no `h3`, `#` headings at block position 0, `legacy_type` residue,
machine-key alt text. Those were found by querying production, not by any test.

Worse, staging *passed* the ten Thai demo tests that could never pass against
production, because staging is seeded and production is not. A green check that
is green only because the environment happens to be seeded is not a signal.

The existing rule that production data must never seed staging is correct and
should stay — it is about customer content. But it was allowed to become
"staging fixtures must be clean", which is a different and unjustified claim.
Nobody's privacy requires staging to lack production's *shapes*. A shape census —
distributions, key sets, nesting patterns, locale asymmetry — can be reproduced
with entirely synthetic content.

## Proposed changes

1. **Stop creating epochs.** Schema changes become forward-only migrations
   against the existing production resource. `migrations/` accumulates; length is
   not a defect.
2. **Delete the rule at `release-and-outage-prevention.md:124`** and the write
   freeze it requires. `DB_WRITE_FROZEN` and `server/utils/database-write-freeze.ts`
   go with it.
3. **Delete the epoch documents and the per-epoch transfer tools** once no epoch
   is in flight. Retain `migrations-archive/` as history.
4. **Rebuild staging fixtures from a production shape census**, not from clean
   generated content, so imported shapes are exercised before customers meet them.
5. **Make stated verification requirements executable.** `release-and-outage-prevention.md:71`
   already requires that verification confirm *referenced assets* have converged;
   `scripts/wait-for-nuxt-deployment.mjs` checks only HTML and build ID. That gap
   caused the NCLS 404. A requirement written in prose and not enforced in code is
   worse than not writing it.

## What this proposal does not claim

It does not claim the Epoch 6 transfer was wrong: it was correct and provably so.
It does not propose changing how migrations are generated or reviewed, and it does
not touch the prohibition on hand-written custom migrations or on patching
production data. It argues only that the rebuild-and-transfer model should not be
how a column is dropped.
