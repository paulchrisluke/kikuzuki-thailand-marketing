# Database epoch 5 cutover

**Status: Staging preparation authorized; production remains owner-controlled.**
**Issue:** #829

Epoch 5 replaces the released Epoch 4 schema on a new D1 resource. The generated
schema has 53 tables: 18 owned by Better Auth and 35 owned by the application,
down from 96 total. Publication roots and translations, request activity,
analytics, settings and provider state now live with their canonical owners.
See [the retained-table audit](epoch-5-consolidation.md) for each boundary.
`server/db/schema.ts` is the only schema source. The baseline is generated by
the pinned Drizzle CLI after the audit; no custom migration is permitted.

The release owner authorized a logging correction and merge into staging after
local and Codex browser verification, without waiting for preview E2E completion.
Production promotion remains owner-controlled and issue #829 stays open. The owner
explicitly prohibits social-card generation; the setup commands below must not
run during this staging qualification.

## Staging preparation

The earlier APAC staging candidate was prepared on September 6, 2026 using the
superseded 94-table baseline. It has not been rebuilt for this consolidation and
does not qualify the 53-table candidate. Private historical parity reports remain
outside Git. The owner has now authorized staging preparation and merge; the obsolete resource remains retained.

Use the existing unreleased-epoch procedure in
[epoch-4-cutover.md](epoch-4-cutover.md#staging). The seed generators deliberately
support local and preview only. Do not pass `--staging` to them, repoint preview,
or copy the production transfer candidate into staging.

1. In a clean local checkout of the final candidate, set `E2E_TEST_PASSWORD`
   privately for fixture provisioning. Staging's read-only OAuth smoke does
   not require that password. Run
   `yarn e2e:local:prepare`, then `yarn fixtures:verify:local`. The preparation
   command applies the generated baseline, runs the four canonical seed
   generators, provisions the existing E2E identities without a local developer
   account, and builds the Worker. Do not export a database already exercised
   by browser/API canaries or containing locally generated media assets.
2. Export that verified local D1 as a private SQLite candidate and record its
   application-table counts and logical hashes. Produce its standard SQLite
   data-only dump with `--escape off`, `--data-only`, `--nosys` and `--newlines`.
   Explicitly select the 53 application and Better Auth tables from the committed baseline;
   `--nosys` does not exclude `d1_migrations` or other Wrangler-owned tables.
   Reject schema statements, migration/system rows and `unistr()` expressions.
   Write UTF-8; Windows PowerShell redirection can otherwise produce UTF-16.
3. Create the fresh resource using
   `yarn wrangler d1 create krabiclaw-db-staging-epoch5-final --location apac --update-config=false`.
   Verify the returned database identity. Update only the `env.staging` D1
   binding to that resource; keep the production and preview bindings intact.
4. Run `yarn wrangler d1 migrations apply DB --env staging --remote`. Confirm
   that only the committed Epoch 5 baseline is recorded and every application
   table is empty. Never apply it to the retained Epoch 4 staging resource.
5. Follow the existing bulk-import procedure: wrap the data-only payload in
   `PRAGMA foreign_keys = OFF;` and `PRAGMA foreign_keys = ON;`, then run
   `yarn wrangler d1 execute DB --env staging --remote --file <private-data.sql>`.
   This is the existing empty-candidate remote import exception; transaction-
   scoped `defer_foreign_keys` is insufficient for Wrangler's remote file import.
6. Export the complete destination with
   `yarn wrangler d1 export DB --env staging --remote --output <private-staging.sql>`.
   Compare every application table against the clean fixture candidate, check
   the baseline and run `PRAGMA foreign_key_check` plus the content/media
   ownership invariants. Commit the verified staging binding before merging
   the feature PR. The ordinary staging deployment then finds its baseline
   already applied.
7. After that Epoch 5 Worker is serving the new database, complete the
   post-start social-card initialization below. This is the final standalone
   staging setup step, before handoff and final read-only card verification.
   Ordinary staging CI remains read-only.

### Post-start staging social cards

The clean fixtures intentionally contain no generated social cards. Staging
has `crons = []`, so waiting for a scheduled backfill cannot complete setup.
Follow the existing [post-start setup contract](../local-development.md) with
`local:cards`, which signs in through Better Auth and uses the dashboard's
normal regeneration endpoints. Keep the fixture password in the process
environment as `E2E_TEST_PASSWORD`; do not put it on the command line.

Run each fixture owner against its own site, then the platform fixture admin
for platform pages and documentation:

```sh
corepack yarn local:cards --base-url https://staging.krabiclaw.com --site-id site-demo --email demo-owner@playwright.example
corepack yarn local:cards --base-url https://staging.krabiclaw.com --site-id site-pottery-house --email pottery-owner@playwright.example
corepack yarn local:cards --base-url https://staging.krabiclaw.com --site-id site-kikuzuki --email kikuzuki-owner@playwright.example
corepack yarn local:cards --base-url https://staging.krabiclaw.com --site-id site-ncls-blawby --email ncls-owner@playwright.example
corepack yarn local:cards --base-url https://staging.krabiclaw.com --platform --email platform-admin@playwright.example
```

These call `POST /api/editor/sites/<site-id>/social-cards/regenerate` and
`POST /api/admin/platform/social-cards/regenerate`. The existing command follows
every cursor, processes five owners per request, fetches every generated or
reused PNG, and checks its 1200×630 dimensions. Require zero failures, inspect
each reported skip, and retain the counts. Re-running reuses matching cards.
Verify the rendered pages' `og:image` URLs and fetched images in the browser
after generation completes.

This one-time write is part of initializing the unreleased standalone staging
epoch. It does not authorize recurring staging writes, fixture reseeding or a
new CI step. After initialization, the staging handoff and verification are
read-only. Production uses the separate owner-controlled step below.

Use the repository-pinned Node and Yarn. On this Windows workstation, invoke
Corepack's JavaScript entry point with the pinned Node executable; the system
`corepack.cmd` otherwise selects a different Node version. Keep exported data,
credentials and raw browser traces outside Git.

## Transfer qualification

Keep source exports, transformed databases and row-level evidence outside Git.
The explicit Epoch 5 transfer must reject undeclared tables or columns and
ambiguous conversions. Its manifest accounts for removed preference and selector
state, retained historical records, and every converted field. Unchanged values
must retain typed logical hashes, including Better Auth sessions, credentials,
OAuth grants, subscriptions, bookings, content and media.

The transfer must prove the opening-minute and recurring-start decisions for
existing customer schedules. Unknown hours and missing business facts remain
unknown. A schema-valid JSON document alone is insufficient proof. Inspect the
rendered pages and availability through the production Worker build.

Run migration lint, unchanged-schema drift, migration-tool tests, the applicable
unit and real D1 tests, quality checks, and the production build. Browser checks
cover CMS editing, public customer journeys and rendered social cards; MCP
checks use the real authenticated runtime. Record the exact source and target
hashes and the qualified commit before provisioning a release candidate.

### Earlier local provider evidence

These checks qualified the earlier implementation, before the 53-table
consolidation. They establish the provider prerequisites below; they do not
replace final candidate runtime and deployed-preview checks.

The earlier generated baseline and verified production projection (94 tables,
42,244 rows) were imported into an isolated local D1 for the actual production
Worker build. Only the existing local developer fixture was provisioned there
using `--local-dev --user-id user-local-developer --persist-to <private-directory>`.
The original verified production candidate remained immutable.

One retained, retrievable `invoice.paid` dead letter passed the canonical
operator preview/apply endpoints and the existing scheduled processor. It
became processed once, with a paid invoice period equal to the original
provider line and matching organization `paid_through`. A correctly signed
duplicate left the full billing-state response unchanged. The retained event
payload, all other 28 event rows, subscriptions, content and media were
unchanged. D1 reported zero foreign-key violations; 86 tables retained their
logical hashes, with changes confined to expected local auth fixtures and
billing projections. Provider operations were reads only, delivery modes were
`log_only`, and GA4 configuration was empty.

The fixture Worker also passed signed Stripe ingress/dedupe and public contact
creation followed by compact signed inbound reply, owner-visible persistence,
duplicate suppression and invalid-address rejection. These checks exercise
the shared ingress domain through the Worker; they do not prove live MIME
transport. Eight existing OAuth tests passed, covering credentialed PKCE,
one-time code exchange, remembered consent, refresh-token issuance and scoped
UserInfo. The existing public CIMD test was then extended and passed an actual
refresh-grant exchange, replacement refresh-token rotation, bearer-only MCP
`tools/list`, and rejection of the consumed refresh token. It checks refresh
before replaying the original authorization code, because Better Auth revokes
that code's issued grants upon code replay. The private JWT assertion test
requires HTTPS and remains a preview gate.

Retained Better Auth session, credential and grant columns passed transfer
hash parity. Replaying a retained session or refresh grant requires the
original client-held cookie or token, which was unavailable. Do not claim that
fresh credentialed OAuth tests prove those retained credentials were exercised.
Sanitized details are in `.audit/829-provider-census.md`; raw evidence remains
under the private `krabiclaw-829-private` directory.

## Provider prerequisites for production

Epoch 5 deletes the old Stripe webhook route and ownership-metadata readers.
The existing `scripts/seed-stripe.mjs` ownership-cutover mode provides an explicit
read-only plan, apply, verify and rollback procedure. The reviewed live plan
contains five customers, three active subscriptions and one webhook endpoint.
It preserves billing terms and canonical Better Auth identity. Canceled
subscription history resolves through its customer and is not rewritten.

Normalize the provider metadata and move the endpoint to
`/api/auth/stripe/webhook` before the production application loses the old path.
Use the exact reviewed plan and verify it; do not hand-edit application data.
No live provider writes are part of staging qualification.

Both retained processed-invoice repair previews returned 409
`reconciliation_evidence_mismatch` in the isolated Worker: the actual Stripe
customers still have `organization_id`, while canonical reconciliation requires
`organizationId` and `customerType: organization`. Active subscriptions likewise
need the reviewed `referenceId` normalization. Their customer IDs and retained
Better Auth subscription rows are present; no ownership metadata was invented
to bypass this gate. After the owner applies and verifies the exact provider
plan, repeat the canonical reconciliation and any required processed-invoice
repair. Unavailable historical provider events must remain recorded as
unreplayed; do not bulk-requeue missing payloads.

Old reply-address formats retire at Epoch 5 under the owner's explicit
no-backwards-compatibility instruction. Preserve all conversation records.
Five historical Epoch 4 source records were marked new and lack completion evidence;
do not claim they were resolved. Current compact reply signatures and their
configured domain must pass the real ingress checks before production.
The local compact-address checks passed. The release owner must separately
verify an actual delivered reply through the provider and Cloudflare email
hook, preserving `EMAIL_REPLY_SECRET` and the configured reply domain.

and [release-flow.md](../operations/release-flow.md). Prepare a fresh APAC

   `DB_WRITE_FROZEN = "true"`; drain prior requests for at least 60 seconds.
3. Take the final production export. Transform and independently verify it.
4. Import data only into the empty Epoch 5 application tables. Export the

6. As an explicit owner-controlled post-cutover operation, regenerate social

   administrator; do not provision E2E identities in production. Supply each

   ```sh
   corepack yarn local:cards --base-url https://krabiclaw.com --site-id <retained-site-id> --email <authorized-tenant-owner-email>
   ```

Preserve the Epoch 4 and Epoch 3 resources, the documented Durable Object
